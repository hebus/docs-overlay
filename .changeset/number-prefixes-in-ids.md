"docs-overlay-docusaurus": patch
---

Model Docusaurus's number prefixes and `id` frontmatter when computing doc ids and slugs.

Docusaurus strips a leading number from **every** path segment, directories included: `040_filters.md`
under `tutorial/` is the doc `tutorial/filters`, served at `/tutorial/filters`. The adapter only dropped the
extension, so for any number-prefixed file it computed an identifier Docusaurus never uses.

The visible symptom was a page that no sidebar mark could reach. The one that matters is quieter:
`pruneMissing()` removes a reference whose doc it cannot find among the version's doc ids, so an **authored**
sidebar entry naming a number-prefixed page would have been pruned out of the navigation, silently, on a
site that had done nothing wrong. Found on a real tree where the prefixed pages happened to be reached
through an `autogenerated` block, which is the only reason nothing broke.

Both patterns are copied from the plugin rather than approximated, including the second one's job of
refusing to strip: `7.0-notes.md` and `2021-11-release.md` keep their names, because a version and a date
both look exactly like a number followed by a separator.

One asymmetry is worth stating, because it is the part a reimplementation gets wrong. The category-index
test compares **raw** names on both sides — `isCategoryIndex` matches `path.parse(source).name` against the
unstripped directory — while the URL it produces is stripped. So `020_guide/020_guide.md` is a category index
served at `/guide`, and `020_guide/guide.md` is not one, and is served at `/guide/guide`. Stripping before
comparing would invent a category index that Docusaurus does not see.

`id` frontmatter is now honoured too, replacing the file name part of a doc id and only that part, which is
how the plugin joins it onto the directory prefix.

`docIdOf`, `docusaurusSlugify` and `declaredSlug` take an options object — `{ pageExtensions,
parseNumberPrefixes }` — and still accept the extensions array positionally, so no call site has to move for
a fix it did not ask for. `parseNumberPrefixes: false` is the plugin's `DisabledNumberPrefixParser`.
